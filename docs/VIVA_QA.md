# IntelliDoc AI: Viva Questions and Answers

Read each answer, then open the file mentioned and find the code yourself. If you can point at the code, you understand it. Say answers in your own words.

**1. Why did you choose this project?**
Almost every organization keeps document records (certificates, invoices, permits), and manual tracking makes searching and spotting expired items slow. It lets me show a full stack: UI, validation logic, database and reporting, in a size I can finish and explain.

**2. What problem does it solve?**
It gives one place to register documents, applies consistent basic checks (required details, expiry), shows status counts at a glance, lets you search/filter, and exports a report. It does not prove authenticity; it is a record-management and rule-based checking prototype.

**3. What is React, and what are components and state?**
React is a JavaScript library for building UIs from components (functions that return JSX). State (`useState`) is data that, when changed, makes React re-render. Here, `docs`, `search`, `statusFilter` and the open dialogs are state. See `App.jsx`.

**4. What is Vite and why use it instead of Create React App?**
Vite is a build tool and dev server. It starts instantly and does fast rebuilds because it serves source files as native ES modules in development and bundles for production with `npm run build`. CRA is no longer recommended.

**5. What is Supabase?**
A hosted backend platform built on PostgreSQL. It gives a database, an automatic REST API, authentication and storage. I use `@supabase/supabase-js` so the browser can query the `documents` table without me writing a server.

**6. Why PostgreSQL and not just browser localStorage?**
PostgreSQL is a real relational database: data is shared across devices and users, survives clearing the browser, and can enforce constraints. Browser localStorage would be per-browser, limited in size (about 5 MB), unstructured and easy for the user to edit, so it is not suitable for shared records.

**7. Explain CRUD and where each part is in your code.**
Create, Read, Update, Delete. In `src/lib/documents.js`: `createDocument` (insert), `listDocuments` (select), `updateDocument` (update by id), `deleteDocument` (delete by id). The UI calls these and updates its state only after they succeed.

**8. What is a primary key? Why a UUID?**
A primary key uniquely identifies each row and cannot be null or duplicated. A UUID is a 128-bit random identifier generated by the database (`gen_random_uuid()`), so IDs are unique without a counter and are hard to guess, unlike 1, 2, 3.

**9. Which database constraints did you use?**
`NOT NULL` on required columns, a `CHECK` so status can only be Pending, Verified or Rejected, `CHECK` that required text is not blank, a default status and `created_at`, and the primary key. They protect the data even if someone bypasses the UI.

**10. What are environment variables and why `VITE_`?**
They keep configuration (URL, key) outside the code. Vite only exposes variables starting with `VITE_` to browser code. `.env` is in `.gitignore` so it is not committed; `.env.example` shows the names. Because they are bundled into the browser, secrets like the service-role key must never go there.

**11. How does the app connect to Supabase, and what if it is not configured?**
`supabase.js` checks whether both variables exist and look valid, and creates one shared client. If they are missing, `App.jsx` shows a setup screen instead of the dashboard. If Supabase is configured but a call fails, the error is shown in the interface (a red panel with Try again, or a message inside the dialog); nothing is silently replaced by other data.

**12. Explain your rule-based validation.**
In `validation.js`: missing title, type or number blocks saving; an expiry date before today means Rejected; otherwise Verified; the user can override the status manually. It is rule-based (fixed if/else logic), not AI, and does not prove authenticity.

**13. How do you avoid date bugs with expiry?**
`new Date("2026-10-11")` is parsed as UTC and can shift the day in other time zones. I keep dates as `YYYY-MM-DD` strings, build "today" from local date parts, and compare strings. A document expiring today is still valid; tomorrow it becomes expired.

**14. How is the CSV generated safely?**
`csv.js` builds a header and one line per displayed record. Any value containing a comma, quote or line break is wrapped in double quotes, with inner quotes doubled (RFC 4180). Values starting with `=`, `+`, `-`, `@` get a leading `'` to prevent spreadsheet formula injection. A Blob and a temporary link trigger the download.

**15. How do search and filtering work?**
`filterDocuments` lowercases the search text and checks whether title, type, number or status contains it, and applies the status dropdown. `useMemo` recalculates the list only when data or inputs change. The CSV export uses the same filtered list.

**16. How do you handle errors?**
Database calls throw readable errors (network, missing table, permission denied, bad key). The UI shows a red message with a Try again button when loading fails, shows save/delete errors inside the dialog, and never says "saved" until the operation really succeeded. A failed update does not create a duplicate record.

**17. What is the security weakness of your anonymous access?**
There is no login, and the demo policies let anyone who has the URL and anon key read, edit and delete every row. Acceptable only for a disposable classroom project with fake data. Never store real personal documents.

**18. What is Row Level Security?**
A PostgreSQL feature where policies decide which rows a user can select, insert, update or delete. With RLS enabled and no policy, access is denied. My demo policies allow everything. For real use I would add Supabase Auth, a `user_id` column and policies like `auth.uid() = user_id` (written in `supabase.sql`, section 5).

**19. How did you test the project?**
Automated tests (`npm test`) for the rules, the expiry boundary, filtering, counts and CSV escaping; manual tests of add, edit, delete, search, filter, export, persistence, errors, mobile layout and the production build, listed in `docs/TEST_PLAN.md`. (Only claim results you actually obtained.)

**20. What are the limitations and future improvements?**
No login, no file upload, no OCR/AI, no audit log, open demo policies, and paging/sorting/search happen in the browser (fine for hundreds of records, not millions). Future: Supabase Auth with per-user RLS, file storage, AI-assisted extraction, expiry reminders, roles and approvals, and deployment.

## Likely follow-ups

- _Why `useMemo`?_ To avoid recomputing derived values on every render; the results are always derived from the same `docs` state, so the cards cannot disagree with the table.
- _Why is the anon key safe to expose?_ It is designed to be public; safety must come from RLS policies. The service-role key bypasses RLS and must never be in the frontend.
- _What happens if two people edit the same record?_ The last save wins; there is no conflict detection in the MVP.
- _How do sorting and paging work?_ The records are loaded once, then sorted and sliced 10 per page in the browser with `useMemo`. For very large data sets this would move into the database query (`order`, `range`).
- _Is this "verification"?_ Only in the sense of rule checks on record details. It cannot tell a genuine certificate from a forged one.
